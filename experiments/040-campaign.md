# 040 — ゲスト内で日常的に開発する

2026-11-16 JST。[指示](040-campaign-prompt.txt)に沿い、通常のCプログラムとして開発用シェルと行エディタを実装した。編集・保存・ビルド・実行・修正・パイプの制御はゲスト内で行う。ホストによる中間コマンドの解釈や生成コードの供給はない。カーネルは039と同一。

## 独立検証

[verify_development.py](../verify_development.py)は空のディスクへ入力ソースを投入し、種から再構築した。コンパイラは3世代とも65,412バイト。各インストール先の全コードと生成コードが一致し、連続する自己ビルドも一致した。SHA-256は`9bef5076693902e05c3a7a612b50c039fdd8317b21efc2f8a8b5554c1fe19d1a`。開発シェルは38,248バイトだった。

- 観測側が新たに選んだCソースをエディタで行挿入して作成し、保存・ビルド・実行した。行置換・削除・未保存変更の破棄を確認した。不正なソースを保存してビルドを失敗させても、編集前に成功したユーザープログラムが動いた。
- 新しいプログラムは標準入力の小文字だけを大文字へ変換する。NUL・EOT・ランダムバイトを含む入力で、入力リダイレクト、2段・3段パイプ、出力・追記を照合した。シェルが出力を代用する仕掛けはない。
- 子の`exit(7)`、標準エラーの分離、basenameの引数エラー、入力ファイル不足、不正なパイプリダイレクトの後もシェルと保持済みプログラムが動いた。
- 32,768バイトの3段パイプを通し、2倍の入力で容量エラーを検出した。上限いっぱいのファイルへの行挿入は拒否された。空の出力で既存ファイルを切り詰め、その直後に停止して、ディスク上と再起動後の双方で空を確認した。
- 保存した新しいCソースと全入力がバイト一致した。再起動して種から再構築し、保存ソースのビルド・実行とバイナリ変換パイプを再現した。
- 別の空ディスクで[039のCLI検証](../verify_shared_cli.py)も040のコンパイラとlibcで実施した。原本のecho・cat・basenameの正常系・異常系、前処理・Cの意味、ファイルI/O、失敗ビルドの保持と再起動検証が通った。

観測側の最初の検証では、従来カーネルの`cat nova.c`が名前検査で拒否された。ディスクのソースは保存されており、新しい開発環境の`catbuild nova.c`と再ビルドで検証した。従来シェルの名前制限まで拡張したとは主張しない。

## 成果物と再現

正確な入力名・長さ・ハッシュ・保存先は[入力一覧](040-inputs.json)にある。新規・変更ソースは[コンパイラ](040-compiler.c)、[libc](040-libc.c)、[開発シェル／エディタ](040-development.c)。[ゲストで編集した例](040-editor-example.c)、[出力](040-output.txt)、[引き継ぎ](040-handoff.txt)、[トランスクリプト](040-transcript.md)も保存した。原本の4つの上流入力は変更していない。共通ヘッダ・中継コンパイラは039を再利用する。

ソースを一覧のゲスト名へ投入した後、各行を入力する。

```text
as new1
install
build extra1
install
build extra3
install
build raw
install
build extra2
install
build extra4
exec dev
```

以降は`dev> `で操作する。

```text
edit new.c
i 1 #include "libc"
i 2 int main(void){puts("hello");return 0;}
w
q
build new.c
exec hello
new.c | catbuild > output
Check tail >> output
catbuild output
quit
```

エディタの`p [N]`は表示、`i N TEXT`は挿入、`r N TEXT`は置換、`d N`は削除、`w`は保存、`q`は最後の保存以降を破棄して戻る。`remove FILE`で不要ファイルを削除できる。24スロットすべてを使った保存スナップショットでは`poem`と`orbit.c`が破棄可能。

独立検証は以下で再現できる。検証用ディレクトリは`guest.hex`と、一覧のゲスト名を持つ`files/`で構成する。

```sh
python3 verify_development.py SNAPSHOT_DIRECTORY
```

## 実装と制約

コンパイラの関数上限を32から64へ広げ、一般のアドレスを呼び出す`invoke`とUART出力の`uartput`を追加した。libcの通常関数`putchar`は標準FDを通るため、原本echoの改行もパイプに入る。libcにFD16/17のメモリストリーム、標準FDの継承、追記用開始処理を追加した。開発シェルはコンパイラを直接呼び、別領域へ生成してからユーザーコードを置き換える。

配置は、カーネルの実行コード`0x40140000`、コンパイラ`0x40150000`、生成用`0x40b00000`、保持ユーザーコード`0x40c00000`、パイプの一時コード`0x40d00000`。エディタ`0x40e00000`、ソース読込`0x40e40000`、2本のストリーム`0x40f00000`と`0x40f08000`を分離した。生成上限65,532バイトに対してコンパイラの余裕は120バイト。

パイプは最大8段、各中間出力32 KiBの逐次実行。最初の非ゼロ終了で残りを中止し、既に行った書き込みは戻さない。並行実行やPOSIXシェル全体を実装したものではない。空白区切りの演算子と引用文字列を扱い、変数・glob・エスケープ展開はない。裸のソース名はその場でコンパイルする。`build`は保持ユーザーコードを作り、`exec`はそれを使うため、パイプを実行しても保持コードは失われない。

ファイル24個、名前12バイト、各32 KiB、前処理出力30,000バイト、コマンド4,095バイト／64トークン、編集コマンド1,023バイト。Cは引き続きサブセット。コンパイル済みコードはRAMのみで、保存ソースから再構築する。物理ディスク障害注入、任意コードからのメモリ保護、完全なPOSIX互換性は検証範囲外。ゲスト内の自己検証手順と修正経緯は引き継ぎに残した。

Piの起動5回、続行指示なし。トランスクリプトは画像0枚で、生成後に認証情報などの混入を確認した。生ログ・観測側の生成バイナリは`.local/`に保存した。
