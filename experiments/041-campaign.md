# 041 — ソース一式から環境を再構築する

2026-11-16 JST。

[指示](041-campaign-prompt.txt)に沿い、ソースだけを持つディスクと明記した起動イメージから、`batch bootplan`の1コマンドで環境を再構築する。種のアセンブル、中継Cコンパイラ、最終Cコンパイラの自己ビルド、共通libcを含む原本CLI、エディタ／開発シェルをゲスト内で生成する。ホストは正確な入力の投入と検証を行い、中間コマンドを解釈・転送しない。

## 信頼する入力

[入力一覧](041-inputs.json)がゲスト名、保存先、バイト数、SHA-256、アーカイブ内部のソースを定める。最初のディスクへ投入するのは`inputs`に並ぶソース14個だけ。生成済みコンパイラ、CLI、開発シェルのバイナリは投入しない。

起動イメージのOS・組み込みアセンブラ・初期のコンパイラは信頼するバイナリであり、OS全体のソース再構築まで達成したとはしない。追加したバッチ処理とローダーのソース、ゲスト内の組み立て・差分生成手順、正確なカーネル差分も保存する。コード生成器が持つAArch64命令テンプレートと、生成済み最終コンパイラの埋め込みは区別する。後者は入力にない。

## 独立検証

[検証スクリプト](../verify_environment_rebuild.py)が完全に新しいゼロのディスクを2つ作り、各々へ同じ宣言入力だけを入れた。ゲスト側のハッシュ一覧をホストのSHA-256と照合し、入力ファイルと全アーカイブメンバーのバイトを確認した。原本のecho.c、cat.c、basename.c、arg.hは固定済み上流入力に一致する。

コンパイラは65,412バイト、SHA-256は`9bef5076693902e05c3a7a612b50c039fdd8317b21efc2f8a8b5554c1fe19d1a`。ビルド計画内で連続する自己ビルドを全65,532バイトの領域について比較し、末尾のゼロ埋めも含めて2回一致した。観測側も実際のインストール先と生成物の全バイトを照合した。

保存形式は4バイトのコード長と機械語。32 KiBを超えるものだけ2ファイルへ分割する。2つの空ディスクから得たコンパイラ、開発シェル、cat、basename、echo、SHAツールの全8保存ファイルがバイト一致した。コード長と保存形式込みの長さ・ハッシュは入力一覧の`code`と`outputs`を参照する。

再起動後は`enter devbin devbin.2 dev restore ccbin ccbin.2`だけで生成した環境を読み込んだ。原本CLIの正常系・異常系を上流のホスト参照と比較し、エディタで新しいCソースを作成した。行挿入・置換・削除・未保存変更の破棄、編集後の不正ビルドで旧USERを保持すること、修正・再ビルド・保存・再起動を確認した。新しいCプログラムがNUL・EOT・ランダムバイトの標準入力を変換し、2〜3段のパイプ、追記、標準エラーの分離、非ゼロexit、エラー後の復帰も通った。空出力での切り詰めは直後に停止してディスク上でも確認した。

不正なアセンブリ、不正なC、欠落した中継ソースを別の新規ディスクで試し、失敗後に次のinstallを実行せず、対話操作へ戻ることを確認した。追加した[境界検証](../verify_rebuild_boundaries.py)では、終了後の全コンパイラバイトを照合し、復元なしの再入場後の自己ビルドも全バイト一致した。別のCプログラムを直接読み込んで`exit(7)`を実行した後も、コンパイラは保持された。不正な整列・容量・長さ・欠けた後半ファイルを拒否し、既存の実行領域とコンパイラを保持した。終端LFのないバッチ、NULを含むバッチ、上限を超える行も実行前に拒否し、その後の対話操作へ戻れた。

最終カーネルでABI・最大容量ビルド／インストール・同じVMでのプロセスI/O、前処理とCの意味、共通CLI一式、ブラウザリンク移動の回帰検証も通った。ゲストが報告した起動イメージのSHA-256もホストの原本と一致した。

## 再現

039の報告にある比較用の上流参照を用意し、リポジトリ直下で実行する。ホストで生成した参照コードはゲストへ渡さない。

```sh
python3 verify_environment_rebuild.py experiments/041-inputs.json \
  .local/echo-reference .local/cat-reference .local/basename-reference
python3 verify_rebuild_boundaries.py RESULT_DIRECTORY/clean-1
```

後者の`RESULT_DIRECTORY`は前者の出力の`work`。最初のコマンドが2つの空ディスク、全入力、生成物、シリアルログと結果JSONを`.local/`へ残す。

生成した環境では`@NAME`で保存バイナリを選び、通常のソース名はCとしてビルドする。どちらも同じFDとパイプを使う。`@echo hello | @cat`、`@cat < input > output`、新しいCソースと`@cat`の組み合わせが使える。`build FILE`／`exec ARGV0`は保持USERを使うため、パイプはUSERを上書きしない。

`extract ARCHIVE NAME`でソースを取り出せる。ソースをまとめたアーカイブは通常のデータで、名前長1バイト、データ長2バイト、名前、データの繰り返しと最後のゼロ。初回の構築では種をアーカイブへ残して、使用済みの展開ファイルを削除することで24スロットに収める。ソースと生成物を失わず、生成環境から初期入力へ戻す`cleanplan`も保存する。これはディレクトリ上の削除で、ディスクの物理消去ではない。独立検証の2回は、これとは別に本当に新しいディスクを使用した。

## 制約と経緯

ファイル24個、名前12バイト、各32 KiB、機械語65,532バイト、前処理出力30,000バイト、逐次パイプ8段／中間出力32 KiBという制約は続く。`@NAME`は後半ファイル名の`.2`を付けるため名前10バイトまで。起動側バッチはLF終端の印字可能ASCII、1行126バイトまでで、ブートストラップに使うas・install・build・execを対象にする。C製ビルド計画は32 KiB、1行4,095バイトまで。Cはサブセット。通常の行編集とソースの再構築が対象で、OS全体の再構築や完全なPOSIXシェル、メモリ保護を達成したものではない。

初回はインストール済みコンパイラからのビルド計画だけで終了したため続行した。その後の独立検証で、保存環境の終了時にインストール済みコンパイラの4バイトが変わり、復元なしの再入場で自己ビルドが応答しなくなる問題を発見した。観測結果を伝えるため途中成果を保存して実験セッションを中断・続行し、復帰経路を修正した。最終版は終了・再入場・自己ビルドと全バイト照合を含む検証を通った。
